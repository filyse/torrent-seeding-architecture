# Очереди переноса и проверки

Лишняя работа ждёт слот. На SSD перенос и проверка считаются отдельно.
На HDD и на диске, тип которого не удалось прочитать, одна очередь на диск.

## SSD

| Очередь | Где считается | Лимит по умолчанию |
|---------|----------------|--------------------|
| Перенос с движка и на движок | API | 4 (`migrate_per_engine`, 1–16) |
| Проверка на одном движке | движок | 2 (`hash_per_engine`, 1–8) |

Перенос занимает слот источника и слот приёмника на всё время копии и
следующей проверки. С `a1` на `a2` идут не больше четырёх копий сразу.
Пятая ждёт, даже если на другом SSD свободно.

## HDD

Одна очередь на движок, лимит `disk_per_engine` (по умолчанию 4, диапазон 1–8).
В неё входят:

- проверка после рестарта, кнопка «Перепроверить» и хеш в конце переноса;
- копирование на этот диск и с этого диска;
- финальная сборка загрузки файла. Чанки по сети слот не держат.

`migrate_per_engine` на HDD не считается второй раз. Смешанная пара
SSD↔HDD: сторона SSD занимает старую очередь переноса, сторона HDD —
слот диска.

Когда работа заканчивается, стартует следующая. Уже начатую проверку
не прерывают. Перенос и сборка файла встают впереди ожидающих проверок
и между собой идут по очереди. Волна хешей после рестарта не блокирует
новый перенос. Ручная перепроверка — обычная проверка, она не обгоняет волну.

Хеш переноса остаётся в слоте приёмника: между копией и проверкой слот
не отдаётся, и более новый перенос его не обгоняет. Слот источника
отпускается сразу после чтения. Отмена отпускает оба слота. Если хеш
уже начался, он дочитывается.

Пятая работа ждёт. Пока она ждёт, бейдж раздачи — «Очередь · перенос»
или «Очередь · проверка». Идущая копия и хеш после неё остаются
«В работе · перенос». Отдельного статуса торрента для диска нет. Окно
загрузки, если сборка не попала в слот сразу, пишет «Очередь · сборка»,
а когда слот выдан — «В работе · сборка» (`complete` → 202).

Один и тот же торрент второй слот не берёт. Кнопка перепроверки во время
переноса этой раздачи ничего не делает.

Снижение лимита не обрывает то, что уже идёт. Новые старты ждут, пока
идущих не станет не больше лимита. Повышение лимита запускает ожидающих
сразу.

Если API умер, слот с арендой гаснет (около 90 с без продления) и его
можно занять снова. Повтор переноса берёт слот заново и не ставит второго
писателя на те же файлы. Рестарт движка посреди копии очищает очередь в
памяти; возобновление снова берёт слот и встаёт впереди волны проверок.

Короткий resume, которым очередь отличает готовый сид от полного хеша,
тоже занимает слот.

Движок без этого метода (старый образ) отвечает 404. API не ждёт его
и считает сторону по очереди переноса SSD.

## Общее

Источник на время копии стоит на паузе в libtorrent. Это не пауза
пользователя: статус в базе `migrating`, сверка очереди его не затирает,
кнопки «Пауза» и «Старт» перенос не снимают. Пока проверка ждёт слот,
в снимке это «Очередь · проверка», а не пауза. Ожидание не считается неполной
копией, и перенос не обрывается.

`auto_managed` у раздач выключен, поэтому `active_checking` libtorrent
их не ограничивает: движок сам добавляет раздачи из fastresume на паузе
и снимает паузу только в свободный слот.

Сначала слот тратится на короткий resume, чтобы отличить готовый сид от
полного прохода. Сид отпускает слот сразу. Обычное `downloading` тоже
отпускает слот: это недокачанная раздача, её надо продолжать. Исключение —
`hold(recheck=True)`: файлы на диске уже целые, а fastresume записан по
пустому каталогу. Такую раздачу очередь не отпускает в рой, а ставит
в проверку хеша. Ручная пауза пишется в `.state/user-paused.json`, и
очередь её не снимает.

## Настройки

**Настройки → Лимиты → Очереди переноса и проверки.** Только admin.

`GET` и `POST /api/v1/settings/work-queues`

```json
{ "migrate_per_engine": 4, "hash_per_engine": 2, "disk_per_engine": 4 }
```

Пустая запись в `app_settings` (`work_queues`) берёт env
`SEEDING_MIGRATE_PER_ENGINE`, `SEEDING_HASH_PER_ENGINE` и
`SEEDING_DISK_PER_ENGINE`.

Новый лимит переноса виден следующей задаче, без рестарта API.
Лимит проверки и лимит диска API шлёт на движки
(`POST /internal/v1/session/hash-limit` и `/session/disk-limit`)
и повторяет при регистрации движка. Старый движок без метода отвечает
404 — настройка в БД всё равно сохраняется.
