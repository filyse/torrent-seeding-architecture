# Переход на libtorrent 2.1.2

Движки сидят на библиотеке Rasterbar, не на отдельном клиенте. Сейчас это пакет
Debian Trixie `python3-libtorrent` **2.0.11** (`engine/Dockerfile`). В sid тот же
2.0.11, через `apt` новее не поставить.

Последняя библиотека — **2.1.2** (25 сентября 2026). Колесо PyPI
`libtorrent==2.1.2` есть под Python 3.13 и `manylinux`, то есть под интерпретатор
образа Trixie. Параллельная линия 2.0 — **2.0.15**, это обслуживание старой ветки.

Поверх 2.1.1 в этом релизе починены переполнение при разборе resume, гонка
`async_hash()` с `force_recheck()` и гонка остановки раздачи с потоками хеша.

Точка отката кода и образа — релиз [`v2026.09.29`](https://github.com/filyse/torrent-seeding-architecture/releases/tag/v2026.09.29),
коммит `079398c`: web 1.53.92, api 1.26.10, engine 1.6.13.

## Что этот переход не делает

- Скорости проверки на одну раздачу в 2.1.2 нет. Счётчик по `piece_finished_alert`
  остаётся.
- Очередь проверок, `v1_only` при создании `.torrent`, отключение DHT/PEX/LSD
  у приватных раздач — остаются.
- `api` и `web` от версии библиотеки не зависят. Их образы не пересобирать.

В 2.1.2 проверка файлов читает кусок целиком, а не россыпью блоков. Очередь слотов
при этом та же.

## Формат fastresume

2.1.2 читает resume, записанный 2.0.11 (`file-version` 1). После своего сохранения
пишет `file-version` 2. Образ 2.0.11 этот файл не читает: раздачи уйдут в полную
проверку. Откат кода без архива `.fastresume`, снятого до первой записи на 2.1.2,
эту волну не отменяет.

`session.state` (`save_state` / `load_state`) на 2.1.2 по-прежнему работает.
Вызовы устарели ещё в 2.0, в коде движка они живы (`torrent_runtime.py`).
Перенос на `session_params` не нужен, пока эти методы отдаются.

## Образ

`engine/Dockerfile` (engine 1.6.14) ставит колесо с релиза GitHub, не с PyPI:
индекс PyPI на 2.1.2 пустой, `pip install libtorrent==2.1.2` не находит версию.

```
pip3 install --break-system-packages \
  https://github.com/arvidn/libtorrent/releases/download/v2.1.2/libtorrent-2.1.2-cp313-cp313-manylinux_2_17_x86_64.manylinux2014_x86_64.whl
```

Пакет Debian рядом не оставлять. `GET /health` отдаёт `version` движка и
`libtorrent_version` модуля. На канарейке во втором поле должно быть `2.1.2.0`.

WebTorrent в колесе собран внутрь, ключа `enable_webtorrent` нет. Сессия при
старте ставит `webtorrent_stun_server=""` и `max_webtorrent_offers=0`. Чужое
имя в `apply_settings` отменяет весь пакет настроек, поэтому на 2.0.11 эти
ключи не передаются.

## Что прогнать до канарейки

На колесе 2.1.2 (проверка с Windows-колеса cp312, тот же релиз; Docker на этой
машине нет, linux-образ ещё не собирался):

1. `lt.session()`, `save_state`, `load_state` — проходят. `listen_on` жив, помечен
   устаревшим.
2. `read_resume_data` / `write_resume_data_buf` в модуле есть. Файл resume,
   записанный живым 2.0.11, здесь не читался: колесо 2.0.11 на этой машине не
   загружается (нет DLL). Это остаётся проверкой канарейки: после старта смотреть,
   ушло ли в `checking_files`.
3. Creator: старый `file_storage` + `create_torrent(..., v1_only)` + `set_piece_hashes`
   с колбэком отрабатывает и пишет v1 (`pieces`, без `meta version`). Вызовы
   помечены устаревшими, путь не менялся.
4. `alert_category.piece_progress` и `save_resume_data_alert` на месте.
5. Флаги `peer_info` те же, кроме `utp_socket` и `ssl_socket`: констант больше нет,
   подпись пира их просто пропускает.

## Выкат

1. Свежий архив `.fastresume` и `session.state` этого движка. Суточный бэкап
   подходит, если он новее последней записи resume. Иначе снять архив руками
   до рестарта.
2. Один движок, не самый большой диск и не пачкой с остальными. b1 для первой
   пробы не брать: там больше всего раздач, волна проверки упирается в диск
   даже при лимите 2 слота.
3. Смотреть: сколько раздач село в `checking_files`, а не в `seeding`; анонс
   на трекер; отдача; лог `drop torrent handle`. Короткий resume без полного
   прохода — норма. Массовый `checking_files` при живых файлах — повод остановиться
   и вернуть архив.
4. Остальные движки по одному диску. Следующий — после того, как канарейка
   отсеялась и сохранила resume уже на 2.1.2.
5. После канарейки дописать `docs/DEPLOYMENT_STATE.md`. Версия движка уже
   **1.6.14**: `CHANGELOG.md` и `engine/README.md` описывают образ, не выкат.

## Откат

- Образ и код: тег `v2026.09.29`.
- Состояние раздач: архив `.fastresume` и `session.state`, снятый до первой
  записи этим движком на 2.1.2. Вернуть архив на место и только потом поднять
  старый образ.
