# Отдача, скачивание и всего отдано по WAN-каналам (экран «Сеть»)

Разбивка текущей **отдачи**, **скачивания** и накопителя **всего отдано** по внешним
каналам (аплинкам) и по движкам внутри каждого канала: сколько уходит/приходит через
каждого провайдера, насколько заполнен канал и кто из движков его грузит.

«Скачивание» = payload libtorrent (`download_rate`) **плюс** заливка файлов из
меню «Файл» (браузер → движок). Оба потока входящие на хост движка и садятся на
тот же WAN, что и торрент этого движка.

«Всего отдано» = payload libtorrent `total_uploaded` (`all_time_upload`) по текущей
инкарнации на движке. Совпадает с чипом в шапке. Это **не** колонка «Отдано» в списке
раздач: там накопитель БД, который переживает перенос.

Версии: `web 1.25.0` / `api 1.16.0` (графики отдачи: ось, наведение, честные пустые корзины).

## Зачем и почему это вообще возможно

Ключевое свойство нашей топологии: **каналы физически раздельные, а не
mwan3-балансировка**. Каждый хост с движками сидит за своим роутером и своим
провайдером:

| Канал | Роутер | Внешний IP | LAN-подсеть | Движки |
|-------|--------|------------|-------------|--------|
| WAN1 | R1 | 88.204.56.176 | `192.168.1.` | b1–b6 (хост `192.168.1.171`) |
| WAN2 | R2 | 88.204.18.1 | `192.168.2.` | a1–a3 (хост `192.168.2.243`) |

Поэтому привязка «движок → канал» **однозначна** и выводится из подсети в URL движка,
который реестр и так знает. Никакого опроса движков ради этого не делается.

> Если бы стояла балансировка (mwan3), канал выбирался бы роутером **на каждое
> соединение**, движок не знал бы, через какой аплинк ушёл конкретный пир, и посчитать
> отдачу по каналам со стороны движка было бы принципиально невозможно — пришлось бы
> снимать счётчики с интерфейсов роутера.

## Компоненты и поток

```
web (/network = отдача, /network/download = скачивание, /network/uploaded = всего отдано)
  → api  GET /api/v1/network/links     — СТАТИКА: карта каналов (один раз при открытии)
  → api  WS-канал `stats` / GET /session/stats
                                       — ЖИВЫЕ скорости и накопители libtorrent: by_engine
  → api  GET /api/v1/network/uploaded-history
                                       — дельты за корзину (только вкладка «Всего отдано»)
  → queue cron 15 мин                  — пишет upload_samples из session/stats
  → очередь «Файл» на клиенте          — входящая заливка, только на /network/download
```

- **`db/seeding_db/wan_links.py`** — карта каналов: id/имя/роутер/внешний IP, список
  префиксов LAN-подсетей и ёмкость аплинка. `link_for_url()` сопоставляет URL движка каналу.
  API реэкспортирует модуль; queue-воркер импортирует его напрямую (в образе очереди нет
  `seeding_api`).
- **`api/seeding_api/routers/network.py`** — `GET /network/links`: раскладывает
  `pool.specs` по каналам. Движки не опрашиваются, эндпоинт дешёвый.
  `GET /network/uploaded-history` — дельты из `upload_samples`.
- **`web/src/main.ts`** — экран `/network` (`mountNetworkShell`), карточки каналов
  (`wanCard`) и строки движков (`wanEngineRow`). SVG-графики — `web/src/uploadChart.ts`.

## Живые данные — без нового поллинга

`EnginePool.aggregate_session_stats()` **и раньше** клал разрез по движкам в тот же ответ,
что и агрегаты для верхней панели:

```python
return {**total, "engines_ok": …, "engines_total": …, "by_engine": by_engine}
```

Фронт этот `by_engine` просто игнорировал — его не было в типе `SessionStats`. Теперь он
объявлен, и экран «Сеть» считает разбивку из **уже существующего** потока: WS-канал
`stats` (пуш), плюс редкий поллинг `GET /session/stats` как бэкстоп. Дополнительной
нагрузки на движки фича не создаёт.

Поля `by_engine.<id>`: для отдачи — `upload_rate`; для скачивания — `download_rate`;
для «всего отдано» — `total_uploaded`; общие — `peers`, `torrents_active`, `error`,
плюс `total_downloaded` в метаданных карточки скачивания.

Заливка файлов **не** приходит с API: фронт суммирует живые `speedBps` очереди
(`fileUploadInboundByEngine`) по `engine_id` и добавляет к приёму канала. Чип
«Скачивание» в шапке показывает ту же сумму.

## Что показывается

**По каналу (отдача / скачивание):** текущая скорость (↑ или ↓), доля от общей,
**утилизация в % от ёмкости** со шкалой (жёлтая с 70%, красная с 90%), движков онлайн,
пиров, активных раздач, отдано/принято всего. На скачивании, если идёт заливка файлов,
под скоростью — «торрент … · файлы …».

**По каналу (всего отдано):** объём в байтах (живой накопитель `all_time_upload`),
доля от общего накопителя (шкала доли, не утилизация канала — ёмкость к счётчику
не применима), движков онлайн, пиров, активных раздач. Над сеткой карточек —
график фермы (стек WAN1+WAN2) и переключатель периода день / неделя / месяц.
В карточке канала — мини-график того же периода между крупной цифрой и шкалой
доли. Столбик = **дельта за корзину** (час или день), не бегущая сумма и не
колонка «Отдано» в списке раздач. Пока сэмплов мало, график честно короткий.

**По движку внутри канала** (сортировка по текущей отдаче / приёму / объёму — сверху
те, кто грузит аплинк или отдал больше): id, скорость или объём, доля внутри канала,
пиры, активные раздачи. Недоступные движки (`error`) показаны приглушённо как
«офлайн» и не учитываются в суммах.

Движки, чья подсеть не сопоставлена ни одному каналу, собираются в карточку «Вне карты» —
чтобы новый хост в незнакомой подсети не выпал из статистики молча.

## Единицы измерения (важно)

- `upload_rate` движка — **байты/с**;
- `capacity_bps` канала — **биты/с**.

Поэтому утилизация считается как `rate * 8 / capacity_bps`. Ошибка в этом множителе даёт
расхождение ровно в 8 раз — тест `test_capacity_is_in_bits_per_second` фиксирует единицы.

Отдельно: наши цифры — это **payload libtorrent, без протокольного оверхеда** (DHT,
трекеры, запросы кусков, uTP-ACK, ip-overhead). Реальная загрузка канала выше на 5–15%,
плюс там же живёт весь не-торрент трафик. Честную загрузку показали бы только счётчики
WAN-интерфейсов на R1/R2 — это осознанно не реализовано. На экране есть сноска об этом.

## Конфигурация

По умолчанию карта зашита в `_DEFAULT_LINKS` (топология выше, **1 Гбит на каждый канал**).
Переопределяется переменной окружения `SEEDING_WAN_LINKS` — JSON-массив той же формы, без
пересборки образа:

```json
[
  {"id":"wan1","name":"WAN1","router":"R1","wan_ip":"88.204.56.176",
   "subnets":["192.168.1."],"capacity_bps":1000000000},
  {"id":"wan2","name":"WAN2","router":"R2","wan_ip":"88.204.18.1",
   "subnets":["192.168.2."],"capacity_bps":1000000000}
]
```

Поведение при кривом значении — деградация, а не падение: невалидный JSON или не-массив →
лог-warning и дефолтная карта; отдельный битый элемент пропускается, остальные работают.
`capacity_bps: 0` = ёмкость неизвестна, шкала утилизации просто не рисуется.

## Эндпоинт

`POST /api/v1/network/links/{wan_id}/limits` (`operator`) — штамп тех же
`download_limit` / `upload_limit` (байт/с, 0 = снять) на **каждый** движок канала.
Это не потолок суммы аплинка: шесть движков по 50 МБ/с дают до 300 МБ/с на WAN1.
Пишется в реестр как обычный лимит движка и сразу применяется к живой сессии.
Неизвестный `wan_id` → 404. UI: «Настройки → Лимиты → Лимиты каналов».

`GET /api/v1/network/links` (`require_auth`):

```json
{
  "links": [
    {"id":"wan1","name":"WAN1","router":"R1","wan_ip":"88.204.56.176",
     "capacity_bps":1000000000,"engines":["b1","b2","b3","b4","b5","b6"]},
    {"id":"wan2","name":"WAN2","router":"R2","wan_ip":"88.204.18.1",
     "capacity_bps":1000000000,"engines":["a1","a2","a3"]}
  ],
  "unassigned": []
}
```

## История отдачи (свои сэмплы)

Prometheus (~15 дней) не используем: горизонт короткий и он не совпадает с
накопителем БД после переноса. Своя таблица `upload_samples`:

| поле | смысл |
|------|--------|
| `sampled_at` | момент снимка |
| `scope` | `farm` / `wan` / `engine` |
| `scope_id` | пусто / `wan1` / `b3` |
| `uploaded` | накопитель в этот момент (как чип «Всего отдано») |

Пишет `sample_upload_stats` в queue-воркере раз в 15 минут одним проходом:
`GET {engine}/internal/v1/session/stats` + карта из `wan_links`. Офлайн-движок
не пишется как 0 (это выглядело бы как сброс) — подставляется последний сэмпл.
Дельта при чтении: `curr >= prev ? curr-prev : curr`. Ферма и WAN в ответе
складываются из рядов движков, чтобы сброс одного не раздувал всю ферму.
Прошлое до деплоя не восстановить.

Периоды: день — 24 часа по часу; неделя — 7 дней по дню; месяц — 30 дней по дню.
Ответ `GET /api/v1/network/uploaded-history?period=day|week|month`:

```json
{
  "period": "week",
  "buckets": [
    {"t": "2026-08-18T00:00:00+00:00", "farm": 123, "wan": {"wan1": 100, "wan2": 23},
     "engines": {"b1": 50}, "sampled": true}
  ],
  "total": {"farm": 123, "wan": {"wan1": 100, "wan2": 23}},
  "previous_total": {"farm": 90, "wan": {"wan1": 70, "wan2": 20}},
  "first_sampled_at": "2026-08-18T00:12:00+00:00",
  "last_sampled_at": "2026-08-24T12:00:00+00:00"
}
```

Фронт дельты не считает. `sampled: false` — корзины до первого / после последнего
сэмпла (штрих «данных ещё нет»), это не ноль отдачи. Историю грузит при открытии
вкладки и при смене периода; WS `stats` SVG не перерисовывает. Выкат: `api` +
`queue_worker` + `web` (движки не трогаем).

## Навигация

Карточки «Отдача», «Скачивание» и «Всего отдано» в верхней панели кликабельны
(`<button>`): `/network`, `/network/download`, `/network/uploaded`. На экране вкладки
переключают сторону. nginx отдаёт `index.html` на любой путь, перезагрузка страницы
не ломает маршрут.

## Тесты

`tests/test_wan_links.py` — карта каналов: дефолтная топология (b*→WAN1, a*→WAN2), единицы
ёмкости, неизвестная подсеть → `unassigned`, переопределение через env, деградация на
битом JSON и пропуск отдельных битых элементов, раскладка движков по каналам.

`tests/test_wan_limits.py` — штамп лимитов только на движки выбранного WAN, чужой
канал не трогается, неизвестный id → 404.

`tests/test_upload_history.py` — дельта накопителя, сброс счётчика, офлайн без нуля,
rollup час/день/неделя, ферма из движков.
