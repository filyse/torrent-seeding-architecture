# Статус раздачи

Колонка `torrents.status` и бейдж в списке — это не сырое состояние libtorrent.
Его пишет `status_from_runtime`: снимок рантайма (раз в ~10 с) и пуш открытой
карточки. Пока идёт перенос или он ждёт слот, статус — `migrating` или
`migrate_queued`, и рантайм (API и `queue_worker`) его не затирает
(`MIGRATION_STATUSES`).

| libtorrent | статус | бейдж |
|---|---|---|
| `seeding`, `finished` | `seeding` | Раздача |
| `downloading`, `downloading_metadata` | `downloading` | Загрузка / Метаданные |
| `checking`, `checking_files`, `checking_resume_data` | `checking` | Проверка |
| `queued_for_checking` | `check_queued` | Ждёт проверки |
| runtime `paused` | `paused` | Пауза |
| runtime `error` | `error` | Ошибка |

Проверка — это проход по уже лежащим файлам (рестарт движка, «Перепроверить»,
хеш в конце переноса). `progress` в этом состоянии — доля прохода, не «сколько
не докачано». Поэтому фильтр «Незавершённые» (`progress < 1`) такие строки
не включает. Ручная пауза важнее проверки: бейдж остаётся «Пауза».

Пока проверка не закончилась, `download_rate` обычно 0: куски из роя не
запрашиваются. После прохода статус сам становится `seeding` или, если файлов
не хватает, `downloading`.

Сколько проверок читают диск сразу — лимит «Проверок на движке»
(`hash_per_engine`, по умолчанию 2). Остальные в снимке
`check_queued`, бейдж «Ждёт проверки» — и в таблице, и на карточке.
Фильтры разные: «Проверка» — только идущий проход, «Ждёт проверки» — только
очередь. Скорость прохода движок считает по `piece_finished_alert` (куски,
которые хешер закончил, за последние 8 с) и пишет в `check_rate`. В таблице
она стоит рядом с бейджем «Проверка».

**Алерты не хранить.** Объект алерта libtorrent жив только до следующего
`pop_alerts()` на сессии. `pop_alerts()` зовётся только в `fastresume_io`
под `ALERT_LOCK`, и каждый `piece_finished_alert` сразу превращается в снимок
`PieceDone(handle, piece)` (копия `torrent_handle` + номер куска). Дальше по
коду ходят только снимки. Нарушение этого правила роняло движок SIGSEGV в
`polymorphic_id_generator<libtorrent::alert>::execute` (см. CHANGELOG
engine 1.6.13.2 / 1.6.17). Тест: `tests/test_alert_lifetime.py`.

**Удалённую раздачу не трогать.** `pause`/`resume`/`force_recheck` идут через
`_call_live(db_id, h, fn)`: под `_lt_lock` и только если `h` всё ещё
`_handles[db_id]`. `remove_torrent` — под тем же замком. Задача очереди
проверки берёт handle заново, когда получила слот. Стресс:
`tests/lt_engine_stress.py`. Полоска «Готово» — только процент.
Пока раздача держит слот очереди, статус остаётся «Проверка», даже если
libtorrent уже показал seeding: иначе фильтр пустой, пока очередь идёт.
«Ждёт проверки» — пауза очереди, не пользователя. Спека очереди: [`WORK_QUEUES.md`](WORK_QUEUES.md).

## Движок недоступен и команды в пути

**Движок недоступен.** Фоновый снимок рантайма (раз в ~10 с) отмечает движок,
который не ответил 2 раза подряд (`seeding_api/engine_health.py`). У его раздач
в списке и карточке `engine_online=false`, бейдж «Движок недоступен» вместо
последнего статуса. Карточка ставит `false` и сама, если движок не ответил на её
запрос. Статус в БД не меняется: когда движок вернётся, бейдж снова верный.
Фильтр состояния `engine_offline`, счётчик `facets.states.engine_offline`.
Счётчики по статусу эти раздачи по-прежнему считают по последнему статусу.

**Команда в пути.** После «Пауза»/«Старт»/«Перепроверить» (по одной и пачкой)
web сразу показывает «Пауза…»/«Запуск…»/«Проверка…» (`pendingOps` в `main.ts`).
Бейдж снимается, когда статус стал ожидаемым (`paused`; не `paused`;
`checking`/`check_queued`), при ошибке запроса, или через 30 с: тогда виден
реальный статус. Пока команда в пути, кнопки пауза/проверка в карточке неактивны.
Состояние только в браузере: после перезагрузки страницы — реальный статус.

## Перенос: очередь и копия

| `migration_jobs.state` | `torrents.status` | бейдж | что происходит |
|---|---|---|---|
| `queued` | `migrate_queued` | В очереди на перенос · №N → цель | ждёт слот «переносов на движок»; раздача работает как прежде |
| `running` | `migrating` | Перенос | источник на паузе, идёт копия/проверка на цели |
| `failed` | `seeding` | (кнопки «Возобновить»/«Отменить») | копия прервана, частичная копия на цели сохранена |

- Задача пишется в `migration_jobs` со `state=queued` **до** ожидания слота
  (`migrate._persist_queued`), поэтому несколько одновременных переносов видны
  как очередь, а не как «Перенос». `№` — `MigrationRepository.queue_position`:
  1 + ждущие раньше задачи с тем же источником или приёмником.
- `GET /torrents/{id}/migrate-status` для ждущей задачи отдаёт `queued`,
  `queue_position`, `source_engine_id`, `target_engine_id`.
- Рестарт API (`recover_orphaned_migrations`): `running` → `failed` и сразу
  возобновляется; `queued` снова встаёт в очередь в прежнем порядке.
  Там же удаляются `failed`-задачи, чья раздача уже на целевом движке.
  `migrate-status` такие задачи тоже не показывает.
- Отмена ждущей задачи (`/migrate/cancel` или удаление раздачи) только снимает
  её из БД: копия не начиналась, источник не ставился на паузу. Ожидающая
  корутина, получив слот, видит, что задачи нет, и выходит.
- Пока `migrating`/`migrate_queued`: pause/resume/recheck → 409. Удаление при
  `migrating` → 409 («сначала отмените перенос»), при `migrate_queued` разрешено.
- Фильтры: состояние «Переносящиеся» включает оба статуса, статус «В очереди на
  перенос» — только ждущие. В facets: `states.migrate_queued`.
