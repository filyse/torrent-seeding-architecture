# Резервное копирование и восстановление

Что копируется каждые сутки, где лежит, как восстановить и как убедиться, что бэкапы
вообще делаются.

## 1. Что копируется, а что нет

| Данные | В бэкапе | Почему |
|--------|----------|--------|
| Postgres (реестр раздач, движков, пользователей, меток, квот) | да, `pg_dump -Fc` | сердце системы, ~1 МБ |
| `.fastresume` каждого движка | да | без него восстановление = полный рехэш всего контента (дни работы дисков) |
| `.torrents` каждого движка | да | позволяет поднять раздачи, не выкачивая метаданные заново |
| `session.state` движка | да | настройки сессии libtorrent, DHT-ноды |
| **Контент раздач (~200 ТБ)** | **нет** | на порядки больше бэкап-диска; восстанавливается ре-сидированием |
| `.env`, сертификаты | нет | секреты, лежат вне репозитория; копировать вручную |

Итоговый объём суточной копии — десятки МБ, поэтому ретеншен в 14 дней ничего не стоит.

## 2. Где и когда

Cron на CT400, ежедневно в 04:30:

```
30 4 * * * bash /opt/containerd/scripts/db-backup.sh >> /var/log/db-backup.log 2>&1
```

Скрипт делает два шага:

1. `pg_dump -Fc` из контейнера БД → `/mnt/media/seeding-test/_backups/db/seeding-<стамп>.dump`.
2. `docker exec containerd-api-1 python3 -m seeding_api.backup_engines` → архивы состояния
   движков в `…/_backups/db/engines/<движок>-<стамп>.tar.gz`.

Каталог `…/_backups/db` смонтирован в контейнер `api` как `/backups`, поэтому UI видит те
же самые файлы, что пишет cron. Диск `/mnt/media` — отдельный от rootfs, копии переживают
пересоздание CT и тома pgdata.

Второй шаг ходит к движкам по внутреннему HTTP API (`GET /internal/v1/meta/archive`), а не
по SSH: у контейнера `api` уже есть реестр движков, TLS и токен. Поэтому бэкап
автоматически покрывает и вновь зарегистрированные движки, и не требует заводить
SSH-доверие с CT400 на хосты движков. Движки опрашиваются последовательно — они на HDD,
и одновременное чтение метаданных мешало бы раздаче.

Настройки: `SEEDING_BACKUP_DIR` (`/backups`), `SEEDING_BACKUP_RETENTION_DAYS` (14),
`DB_BACKUP_RETENTION_DAYS` (14), `SEEDING_BACKUP_STALE_HOURS` (48).

## 3. Восстановление БД — кнопкой

Настройки → «Резервные копии БД» → «Восстановить» у нужной копии. Роль `admin`.

Что происходит: API включает мягкий режим обслуживания (рабочие маршруты отвечают 503,
чтобы клиенты не читали БД во время пересоздания таблиц), выполняет
`pg_restore --clean --if-exists --no-owner` и снимает режим. Маршруты `/health`, `/auth`,
`/backups` остаются доступны, так что UI не «слепнет» во время отката.

После отката проверьте, что состав раздач в списке соответствует ожидаемому: движки живут
своей жизнью и на них могут остаться раздачи, которых в восстановленной БД уже нет (или
наоборот). Расхождения подтягивает `sync_runtime_to_db`.

## 4. Восстановление состояния движка — процедура

Кнопки нет намеренно: это операция на хосте движка с остановкой контейнера, а не
повседневное действие. Порядок для движка `bX` на хосте движков:

```bash
# 1. Забрать архив с CT400
scp <ct400>:/mnt/media/seeding-test/_backups/db/engines/bX-<стамп>.tar.gz .

# 2. Остановить движок, чтобы libtorrent не переписал fastresume при выходе
docker stop bX-seeding

# 3. Распаковать в том движка (имя тома — см. docker inspect bX-seeding)
docker run --rm -v seeding-engine_engine_data:/data -v "$PWD":/src alpine \
  tar -xzf /src/bX-<стамп>.tar.gz -C /data

# 4. Поднять обратно
docker start bX-seeding
```

Если контент на месте, libtorrent поднимет раздачи по fastresume без рехэша. Если контента
нет, fastresume не поможет — торренты уйдут в докачку.

## 5. Как убедиться, что бэкапы живы

В панели «Резервные копии БД» есть строка свежести: зелёная — последняя копия моложе
48 часов, жёлтая с подсказкой — старше. Отдельная строка показывает свежесть архивов
состояния движков и их количество.

Это не украшение. В июле 2026 бэкапы молча не делались **23 дня**: при выравнивании хостов
через `git reset --hard` все `scripts/*.sh` потеряли бит запуска (в git они лежали как
`100644`), и cron падал в `Permission denied` — в лог, который никто не читал. Заметить это
по списку файлов было можно, только вглядевшись в даты.

Что сделано, чтобы не повторилось: скриптам вернули режим `100755` в самом git, cron
вызывает их через `bash` (потеря бита больше не фатальна), а возраст копий виден в UI.

Ручная проверка:

```bash
pct exec 400 -- bash -lc 'bash /opt/containerd/scripts/db-backup.sh'
pct exec 400 -- bash -lc 'ls -lh /mnt/media/seeding-test/_backups/db /mnt/media/seeding-test/_backups/db/engines'
tail -20 /var/log/db-backup.log
```

## 6. Чего бэкап не спасёт

- **Потеря контента.** 200 ТБ не копируются; при отказе диска раздачи придётся качать заново.
- **Секреты.** `.env` и сертификаты не в бэкапе и не в git — храните отдельно.
- **Одна площадка.** Копии лежат на том же хосте (`/mnt/media`), пусть и на другом диске.
  От пожара/кражи это не защищает; вынос копий вовне пока не сделан.
