# Журнал изменений

Учёт фиксов и улучшений по версиям. Версии компонентов независимы:
`web` (`web/src/version.ts`, `WEB_VERSION`) и ядро `api`/`engine`/`queue` (`__version__`).
Бамп — вручную при заметных изменениях; дата сборки пишется в образ (`/BUILD_TIME`).

Формат: `## <компонент> <версия> — <дата>` и список изменений.
Свежие записи — сверху.

---

## web 1.33.0 — 2026-08-24

- **«Откуда» короче.** Вместо «с трекера · он пришёл» — «трекер · вошёл»;
  полный смысл по наведению. Адрес пира не переносится: IP:порт в одну строку.

## web 1.32.0 — 2026-08-24

- **Флаги пиров: кто кого ограничил.** В libtorrent `choked` — это мы его в очереди,
  `remote_choked` — он нам почти не шлёт. Раньше подписи были наоборот, отсюда
  «не отдаём» при живой ↑. Чипы — одно слово: просит, берём, очередь, молчит,
  полный. Если скорость уже идёт — противоречивый чип прячем.

## web 1.31.0 — 2026-08-24

- **Флаги пиров простым языком.** Вместо choke / BEP-10 / сид — «нам не даёт»,
  «не отдаём», «всё есть». Наведение объясняет, что это значит для раздачи.
  Источник: «с трекера · он пришёл».

## web 1.30.0 — 2026-08-24

  простыня `remote_choked, supports_extensions`. Наведение — что значит бит.
  Служебное (ext, MSE) спрятано в «···». Клиент больше не `b'MediaGet2…'`;
  источник — «трекер · вх.», не `33`.

## web 1.16.0 · api 1.8.0 · engine 1.2.0 · tooling — 2026-08-10

- **Починены суточные бэкапы: их не было с 18 июля.** Все `scripts/*.sh` лежали в git как
  `100644`, поэтому `git reset --hard` при выравнивании хостов переписал их без бита
  запуска, и cron на CT400 молча падал в `Permission denied`. Заодно 23 дня не работал
  `disk-guard.sh` (ежечасная чистка docker и слежение за местом). Всем скриптам вернули
  `100755` в самом git — права теперь переживают любой чекаут на всех хостах, — а cron
  вызывает их через `bash`, чтобы повторная потеря бита ничего не сломала.
- **В суточный бэкап добавлено состояние движков** (`.fastresume`, `.torrents`,
  `session.state`). Раньше копировалась только БД, а это состояние живёт в docker-томах на
  хостах движков и не дублировалось нигде: без него восстановление означает полный рехэш
  всего контента. Объём копеечный — десятки МБ на движок.
- **`GET /internal/v1/meta/archive` (engine).** Движок отдаёт своё состояние tar.gz-потоком
  (`w|gz` через пайп — ничего не буферизуется на диске). Контент раздач в архив не входит.
- **Сборщик `python3 -m seeding_api.backup_engines` (api).** Ходит по реестру движков
  (env + БД) и складывает архивы в `$SEEDING_BACKUP_DIR/engines` со своим ретеншеном
  (`SEEDING_BACKUP_RETENTION_DAYS`, 14 дн.). Запускается изнутри контейнера `api` из
  `db-backup.sh`: там уже есть TLS, токен и реестр, поэтому не понадобилось заводить
  SSH-доступ с CT400 на хосты движков. Движки опрашиваются последовательно (HDD), сбой
  одного не валит проход, недокачанный файл остаётся `.partial` и удаляется.
- **Видно, если бэкапы снова встанут.** `GET /backups` теперь отдаёт `latest_at`,
  `age_hours`, `stale` и сводку `engine_meta`, а панель «Резервные копии БД» показывает
  свежесть копий: зелёная строка при норме, жёлтая с подсказкой — если старше
  `SEEDING_BACKUP_STALE_HOURS` (48 ч). Раньше протухание можно было заметить, только
  вглядевшись в даты файлов.
- Ретеншен при первом успешном запуске удалил 15 июльских дампов — им было больше 14 дней.

## api 1.7.1 — 2026-08-10

- **Фикс: «отдано» больше не обнуляется при переносе раздачи на другой движок.**
  Счётчик libtorrent живёт в рамках одной инкарнации торрента: перенос добавляет раздачу
  на цель заново (fastresume не передаётся — копия проверяется рехэшем), поэтому
  `total_uploaded` там стартует с нуля. Снимок рантайма ЗЕРКАЛИЛ это значение в
  `torrents.uploaded_total`, и накопленный объём терялся. Теперь `uploaded_total` —
  накопитель: снимок прибавляет дельту, а не переписывает значение. Объём отданного
  привязан к раздаче, а не к движку или пути.
- **Новая колонка `torrents.uploaded_seen` (миграция `0014`)** — последнее сырое показание
  счётчика текущего движка. Инвариант `uploaded_total - uploaded_seen` = отдано на прошлых
  движках. Уход счётчика назад трактуется как новая инкарнация, а при переносе
  (`update_engine`) база дельт обнуляется явно. Побочно чинится и потеря fastresume:
  раньше она тоже сбрасывала счётчик в UI.
- **Чтение согласовано со снимком** (`runtime_sync.apply_uploaded_carry`): список, деталь,
  `set_limits`/`set_private` и оба WS-канала детали отдают «накопленное + живое», поэтому
  цифра корректна сразу после переноса, не дожидаясь фонового прохода (~10с).
- Миграция инициализирует `uploaded_seen = uploaded_total`, так что первый же тик не
  задваивает объём. Задним числом байты, потерянные при прошлых переносах, не
  восстанавливаются — этих данных нигде нет.

## web 1.15.0 · api 1.7.0 — 2026-08-10

- **Экран «Сеть»: отдача в разрезе WAN-каналов.** Карточка «Отдача» в верхней панели стала
  кликабельной и ведёт на новый экран `/network`. Там по каждому аплинку: текущая отдача,
  доля от общей, **утилизация канала в % от ёмкости** со шкалой (жёлтая с 70%, красная с 90%),
  движков онлайн, пиры, активные раздачи, отдано всего. Внутри карточки — строки движков,
  отсортированные по текущей отдаче: скорость, доля внутри канала, пиры, активные раздачи;
  недоступные движки показаны приглушённо как «офлайн».
- **Карта каналов (`GET /network/links`, `wan_links.py`).** У нас не mwan3-балансировка, а
  физически раздельные каналы: `b1–b6` (LAN `192.168.1.x`) выходят через R1/WAN1, `a1–a3`
  (LAN `192.168.2.x`) — через R2/WAN2. Поэтому привязка «движок → канал» однозначно выводится
  из подсети в URL движка, который реестр уже знает, — **движки для этого не опрашиваются**.
  Топология и ёмкость аплинков (по умолчанию 1 Гбит на канал) переопределяются переменной
  `SEEDING_WAN_LINKS` (JSON) без пересборки образа.
- **Живые данные без нового поллинга.** `aggregate_session_stats` и раньше клал разрез
  `by_engine` в тот же ответ, что и агрегаты, — фронт просто его игнорировал. Теперь он есть
  в типе `SessionStats`, и экран «Сеть» считает разбивку из общего потока (WS-канал `stats`,
  бэкстоп-поллинг `/session/stats`). Дополнительной нагрузки на движки нет.
- Важно про цифры: это payload libtorrent, без протокольного оверхеда (DHT, трекеры, запросы
  кусков, uTP-ACK), поэтому фактическая загрузка канала выше на 5–15%. На экране есть сноска.

## engine 1.1.2 + api 1.5.2 — 2026-07-18

Производительность и «ровность» создания торрентов на HDD-движках (b*), где хеширование
конкурирует за диск с сотнями активных раздач.

- **engine: хеширование вынесено в отдельный процесс** (`multiprocessing`, start method
  `spawn`). Раньше `libtorrent.set_piece_hashes` держал GIL в рабочем потоке и на 2–3с
  подвешивал событийный цикл движка — из-за чего опрос статуса тормозил, а под нагрузкой
  запросы оркестратора падали в таймаут («engine unavailable»). Теперь вся CPU/IO-работа
  идёт в дочернем процессе, а поток-надзиратель лишь качает прогресс через очередь
  (`_hash_worker`, `CreateStatus`-очередь, `_MP_CTX`). Событийный цикл свободен → прогресс
  в UI обновляется плавно, здоровье/опрос движка не деградируют во время создания.
- **engine: число одновременных задач создания — env `SEEDING_CREATOR_WORKERS`, дефолт 1.**
  На HDD параллельное хеширование двух папок вызывает seek-thrashing и замедляет обе;
  последовательная обработка (1 за раз) быстрее суммарно и идёт ровнее. На SSD/NVMe-движках
  можно поднять (`SEEDING_CREATOR_WORKERS=2+`).
- **api: очередь создания опрашивается параллельно** (`GET /api/v1/creator/tasks`,
  `asyncio.gather`) — один занятый HDD-движок больше не тормозит обновление всей очереди в UI.
- Флот пересобран на `engine 1.1.2` (a1–a3, b1–b6), оркестратор — `api 1.5.2`.
  `web` без изменений (остаётся 1.7.1), `queue` — 1.0.0.

## api 1.4.2 — 2026-06-21

- **Фикс 500 на странице раздачи (`GET /torrents/{id}`).** Если одна и та же раздача
  крутится на нескольких движках (напр. после переноса осталась копия), её `info_hash`
  уже занят другой записью. Эндпоинт пытался записать `info_hash` в запись с `NULL` и
  падал с `IntegrityError` (`UniqueViolation` по `torrents_info_hash_key`) → 500. Теперь
  перед записью проверяется наличие записи с таким `info_hash` (`get_by_info_hash`);
  при дубликате запись не выполняется, страница открывается нормально.

## engine 1.0.1 + api 1.4.1 — 2026-06-21

- **Верхняя панель: «Скачивание» показывает только полезные данные (payload).** Раньше
  агрегат брал `download_rate`/`upload_rate` из `session_stats` libtorrent — это весь
  входящий трафик вместе с протокольным оверхедом (DHT, трекеры, запросы кусков, uTP-ACK,
  ip-overhead). При чистой раздаче это давало «фантомные» ~2 МБ/с «скачивания», хотя ничего
  не качается. Теперь движок отдаёт `payload_download_rate`/`payload_upload_rate` (реальные
  данные раздач), с откатом на total только если биндинг не отдаёт payload-поля. При полной
  раздаче «Скачивание» ≈ 0 (engine `torrent_runtime.py`).
- **Верхние карточки обновляются вживую (канал `stats`).** Добавлен лёгкий пуш агрегатов
  сессии в WS-канал `stats` каждые ~4с из `ws_pollers` (та же форма, что у SSE `/stream` и
  `GET /session/stats`). Раньше агрегаты публиковал только тяжёлый цикл полного снапшота
  рантайма, который на больших инсталляциях шёл дольше интервала — карточки «Раздач /
  Скачивание / Отдача» подвисали. Дублирующий пуш из `runtime_snapshot` убран.
- **Фикс молчаливого слома WS-авторизации под uvicorn+wsproto.** Предложенные клиентом
  сабпротоколы (`bearer.<key>`) читаются из ASGI-`scope`, а не из заголовка
  `sec-websocket-protocol` (под wsproto его в `scope["headers"]` может не быть). Из-за этого
  WS уходил в анонимную ветку → `4401` → бесконечный reconnect, и верхняя панель не
  обновлялась. Заголовок оставлен как фолбэк (`routers/ws.py`).
- **Флот приведён к одной версии.** Все 9 движков (a1–a3, b1–b6) пересобраны на
  `engine 1.0.1` с payload-метрикой.
